# INC-2025-018: Checkout failures after Payment Service 4.2 rollout

## Summary and impact

A production degradation affected payment-service 4.2. Customers experienced delayed or failed operations and support observed DB-104. The incident was contained without data loss.

## Timeline

- 14:27 alert crossed the error-budget threshold.
- 14:32 on-call correlated DB-104 with the deployment and dependency dashboards.
- 14:48 the team reproduced the failure in a production-like canary.
- 15:06 containment reduced customer impact.
- 15:41 the permanent corrective change completed verification.

## Detection and logs

```text
2025-06-18T14:32:11Z payment-service ERROR DB-104 request_id=req-7f21 dependency_state=degraded waiting=127
```

## Investigation and root cause

The team eliminated gateway, authentication, and tenant-specific hypotheses by tracing complete requests. The confirmed root cause was 4.2 applied a fixed pool maximum of 40 per pod; with PostgreSQL 16 and 12 replicas this exhausted the 300-session database budget. Similar symptoms can have different causes; in particular, INC-2025-007 and INC-2026-002 both involve Kafka lag but require different corrective actions.

## Resolution and recovery

The responders reduced maximumSize to 24 and minimumIdle to 6, then deployed 4.2.1. They replayed only idempotent work, compared business counters before and after recovery, and kept the incident open until fifteen minutes of stable service-level indicators.

## Contributing factors

The pre-production load profile underrepresented production concurrency. Alert context showed the symptom but not the recently changed configuration. The change review also lacked a dependency-capacity calculation.

## Preventive actions

The owning team added a version-aware configuration test, a deployment canary, and a dashboard joining service replicas to dependency capacity. Future releases must record the calculation in release evidence.

## Related records

Error code DB-104; service guide for payment-service; corresponding customer support tickets and current release notes.

## Triage

The triage objective for payment-service 4.2 is to preserve customer safety while collecting enough evidence to distinguish application health from dependency health. This appendix preserves the validated response pattern learned during the incident. Operators correlate gateway request IDs with payment-service traces and review PostgreSQL 16, Kafka, Redis saturation. A green Kubernetes readiness probe proves only that the process accepts traffic; it does not prove that downstream capacity is available.

For DB-104, the catalog definition is: Database connection acquisition timed out before a checkout transaction could begin. The team checks service error rate, p95 latency, active and waiting connections, Kafka lag where applicable, and the deployment timeline. Evidence is recorded before changing configuration. Commands are executed through approved observability and deployment tooling; secrets and customer payloads must never be pasted into tickets.

Decision criteria are explicit. If the error began within thirty minutes of a version or configuration rollout, compare the live manifest with the release baseline. If dependency saturation is shared by several services, escalate to the platform owner. If only one tenant is affected, examine tenant routing and rate limits. The documented remediation is: For Payment Service 4.2 on PostgreSQL 16 set checkout pool maximumSize to 24, minimumIdle to 6, connectionTimeoutMs to 3000, then deploy 4.2.1, which restores version-aware pool sizing. A canary must complete ten representative operations before broad restoration.

Rollback remains available until verification passes. Restore the previous immutable deployment revision, keep database migrations that are backward compatible, and stop if a downgrade would read data written in a newer incompatible format. Close the phase only after dashboards remain within the service-level objective for fifteen minutes and a synthetic checkout traverses API Gateway, Authentication, Cart, Inventory, Payment, Order, and Notification.
