# INC-2026-006: Notification provider backpressure

## Summary and impact

A production degradation affected notification-service 2.2. Customers experienced delayed or failed operations and support observed NOTIFY-429. The incident was contained without data loss.

## Timeline

- 14:27 alert crossed the error-budget threshold.
- 14:32 on-call correlated NOTIFY-429 with the deployment and dependency dashboards.
- 14:48 the team reproduced the failure in a production-like canary.
- 15:06 containment reduced customer impact.
- 15:41 the permanent corrective change completed verification.

## Detection and logs

```text
2026-02-21T14:32:11Z notification-service ERROR NOTIFY-429 request_id=req-7f21 dependency_state=degraded waiting=127
```

## Investigation and root cause

The team eliminated gateway, authentication, and tenant-specific hypotheses by tracing complete requests. The confirmed root cause was provider quotas were shared across transactional and campaign traffic. Similar symptoms can have different causes; in particular, INC-2025-007 and INC-2026-002 both involve Kafka lag but require different corrective actions.

## Resolution and recovery

The responders split quota pools and prioritized transactional topics. They replayed only idempotent work, compared business counters before and after recovery, and kept the incident open until fifteen minutes of stable service-level indicators.

## Contributing factors

The pre-production load profile underrepresented production concurrency. Alert context showed the symptom but not the recently changed configuration. The change review also lacked a dependency-capacity calculation.

## Preventive actions

The owning team added a version-aware configuration test, a deployment canary, and a dashboard joining service replicas to dependency capacity. Future releases must record the calculation in release evidence.

## Related records

Error code NOTIFY-429; service guide for notification-service; corresponding customer support tickets and current release notes.

The triage objective for notification-service 2.2 is to preserve customer safety while collecting enough evidence to distinguish application health from dependency health. This appendix preserves the validated response pattern learned during the incident. Operators correlate gateway request IDs with notification-service traces and review Kafka saturation. A green Kubernetes readiness probe proves only that the process accepts traffic; it does not prove that downstream capacity is available.

For NOTIFY-429, the catalog definition is: notification-service rejected or could not complete an operation because a required dependency or invariant failed. The team checks service error rate, p95 latency, active and waiting connections, Kafka lag where applicable, and the deployment timeline. Evidence is recorded before changing configuration. Commands are executed through approved observability and deployment tooling; secrets and customer payloads must never be pasted into tickets.

Decision criteria are explicit. If the error began within thirty minutes of a version or configuration rollout, compare the live manifest with the release baseline. If dependency saturation is shared by several services, escalate to the platform owner. If only one tenant is affected, examine tenant routing and rate limits. The documented remediation is: Stabilize the dependency, restore the documented configuration baseline, and verify with a canary request before clearing the alert. A canary must complete ten representative operations before broad restoration.

Rollback remains available until verification passes. Restore the previous immutable deployment revision, keep database migrations that are backward compatible, and stop if a downgrade would read data written in a newer incompatible format. Close the phase only after dashboards remain within the service-level objective for fifteen minutes and a synthetic checkout traverses API Gateway, Authentication, Cart, Inventory, Payment, Order, and Notification.
